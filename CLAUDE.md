# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

Personal environment/dotfiles for two Arch Linux + i3 machines, a **desktop** and a **spellbook**. It is cloned to `~/src/env` on both and its scripts assume that location (`ENV_DIR` defaults to `$HOME/src/env`; `git/gitconfig` and `config/i3/config` spell the path out). The two machines have different usernames, so nothing here may assume a username: use `$HOME`/`~`. There is no build, test, or lint step — changes are validated with `zsh -n` and by running the init against a throwaway `HOME`.

## Layout

- **`init/`** — provisioning. `init.sh` is the bash bootstrap (bash because a fresh box has no zsh yet); everything else is zsh step scripts (see below).
- **`config/`** — files that land in the home directory, laid out by where they go: `zsh/` (`.zshrc`, `.zsh_plugins.txt`, `env/*.zsh` → `~/.zshrc`, `~/.zsh_plugins.txt`, `~/env`), `i3/` (→ `~/.config/i3`), `niri/config.kdl` (→ `~/.config/niri/config.kdl`), `kitty/` (`kitty.conf`, which carries the Skylight colour scheme as well as the font; the niri dropdown terminal needs no kitty config of its own — it is an ordinary window placed by a niri rule, see below), `ssh/config` (→ `~/.ssh/config`, host aliases only; never keys or `known_hosts`), `.xprofile`, `pacman.conf` (→ `/etc/pacman.conf`), `packages.txt` (shared package list), `spotify-mcp/spotify-config.sample.json`, `wallpapers/` (→ `~/pics/wallpapers`, the images `bin/wallpaper` paints on the root window), `avatar.png` (the login-screen face, installed by `init/avatar.zsh` — not linked anywhere).
- **`machines/desktop/`, `machines/spellbook/`** — everything that only one role gets: `machine-role.env` (the role file), `packages.txt` (role-only packages), `i3/*.conf` (role-only i3 config), `niri/role.kdl` (role-only niri config, → `~/.config/niri/role.kdl`), `xprofile.sh` (role-only X-session startup, a POSIX sh fragment sourced by `config/.xprofile`; the desktop one is where the headless Obsidian / Xvfb startup belongs and is a marked placeholder until it is pasted in), `init.zsh` (role init hook, run last), plus role-only config (desktop: `lightdm.conf.d/`, `bin/` with the headless Obsidian / Claude remote-control helpers; spellbook: `greetd/config.toml`, `xsessions/i3-xprofile.desktop`, `autorandr/`, `wireplumber/`, `systemd/`, `logind.conf.d/lid.conf` (lid-switch handling), `ulauncher/`, `bin/`).
- **`bin/`** — scripts for both machines; `config/zsh/env/path.zsh` puts it (`~/src/env/bin`) on `PATH`. It is never linked to `~/bin`, which stays the user's own hand-written-scripts directory (also on `PATH` when present). `claude-hook-node` is the launcher for anything Claude Code has to spawn as `node` (`zsh $HOME/src/env/bin/claude-hook-node <script.js> ...`): it loads node from nvm when Claude Code was started without an interactive zsh (ulauncher, a .desktop entry, a systemd user unit), where PATH has no node. Used by the `node` hooks in `claude/settings.json` and by the spotify MCP server registration, which is why a bare `node ...` is never the registered command. `i3-xsession` is the POSIX-sh wrapper that sources `~/.xprofile` before exec'ing i3, for the greetd path that otherwise skips it (installed to `/usr/local/bin`, not run from here).
- **`git/`** — git helper scripts + the gitconfig include that exposes them.
- **`claude/`** — user-level Claude Code config: `CLAUDE.md`, `settings.json`, `config.sample.json`, `user-skills/*`.

Secrets never live in the repo: `claude/config.json` (Obsidian key) and the Spotify config (client secret + OAuth tokens) are gitignored, and init copies the committed `*.sample.json` into place once for you to fill in.
- **`ide/`** — exported JetBrains configs (binary zips, not editable source).

## Machine roles

`MACHINE_ROLE` is `desktop` or `spellbook`. **Desktop is the default everywhere the variable is unset**: `init/init.sh` (`--spellbook` selects spellbook; `--desktop`/`--desktopMode` are accepted too), `init/init.zsh`, `.zshrc`, `.xprofile`, `path.zsh` and the i3 include all apply `${MACHINE_ROLE:-desktop}`, so a session that never sourced the role file (startx, a display manager that skips `~/.xprofile`) still gets the desktop config rather than silently none. The role is published three ways from one file, `machines/<role>/machine-role.env` (plain `KEY=VALUE`), which `init/role.zsh` links to `~/.config/machine-role.env`:

- **zsh** — `config/zsh/.zshrc` sources it (with `set -a`) *before* the `~/env/*.zsh` loop, so env scripts can branch on it regardless of filename order.
- **X session** — `config/.xprofile` (POSIX sh, because LightDM runs it with `sh`; this is the one deliberate exception to the zsh-only rule, shared by the `machines/<role>/xprofile.sh` fragments it sources) exports it, so i3 and everything it launches inherit it, then sources `machines/${MACHINE_ROLE:-desktop}/xprofile.sh` for role-only login setup. `init/links.zsh` warns loudly before backing up a real `~/.xprofile` to `~/.xprofile.bak`: its contents must be moved into the role fragment or they stop running at login.
- **i3** — `config/i3/config` does `include $HOME/src/env/machines/$MACHINE_ROLE/i3/*.conf`. i3 expands include paths with `wordexp(3)` (env vars, `~`, globs) and silently skips a pattern that matches nothing, so each role dir ships at least one `.conf`.

Desktop-only: gaming/NVIDIA packages, the LightDM HDMI-3 greeter drop-in, `xset s off -dpms`, the Spotify screensaver, Steam + its assign rule, the gamescope rule, and the headless Obsidian / Claude remote-control helpers. The spellbook role is an empty, ready slot (comment-only files).

## The zsh setup

- **`config/zsh/.zshrc`** — the one rc, symlinked to `~/.zshrc`. Reads the role file, then uses [antidote](https://getantidote.github.io/) for plugins (looked for in `~/.antidote`, where `init/antidote.zsh` clones it, then `/usr/share/...` fallbacks) and powerlevel10k for the prompt. Note: the AUR package literally named `antidote` is *unrelated* software (Druide's writing tool), which is why antidote is installed via git clone, not yay.
- **`config/zsh/.zsh_plugins.txt`** — the antidote plugin list (→ `~/.zsh_plugins.txt`). The `ohmyzsh/ohmyzsh path:...` entries are oh-my-zsh plugins loaded *through* antidote; the oh-my-zsh framework itself is gone.
- **`config/zsh/env/*.zsh`** — custom env scripts, sourced from `~/env` (a symlink to the directory) in **alphabetical order**. They have no load-order dependencies; if you add some, prefix filenames (`00-`, `10-`). `globalvars.zsh` exports `EDITOR` and `GRIMOIRE_DIR` (`~/docs/obsidian_vaults/grimoire`, the same on both machines); `path.zsh` adds `~/bin` (the user's own, unmanaged), `~/src/env/bin` and `machines/$MACHINE_ROLE/bin` to `PATH`.

**There is deliberately no per-machine zsh directory.** Every env script is shared; the only role-dependent thing in any of them is the `machines/$MACHINE_ROLE/bin` branch in `path.zsh`, and two guarded lines do not justify a loading mechanism. If one ever does, the shape is settled: `machines/<role>/zsh/*.zsh`, sourced from `.zshrc` in a second loop after the shared `$ZSH_CUSTOM/*.zsh(N)` pass so a role script can override a shared one. That needs **no init change and no placeholder files** — zsh expands `$MACHINE_ROLE` and globs natively, so neither of the workarounds the other role splits need applies (niri's fixed-path `role.kdl` symlink exists because its `include` expands only `~`; the "every role ships at least one `i3/*.conf`" rule exists because `wordexp` silently skips an empty glob — zsh's `(N)` qualifier already makes an absent directory a no-op). Until then, a small difference stays inline the way `path.zsh` does it.

Two things that look like they want a role split and do not:

- **`clip` in `alias.zsh`** is X-vs-Wayland, not desktop-vs-spellbook. The spellbook boots either i3 on X or niri on Wayland, so a `machines/<role>/` answer would be wrong every time it came up under i3; the alias branches on `$WAYLAND_DISPLAY` instead (`wl-copy` vs `xclip`).
- **The terminal colours** are identical on both machines, because both run the same wallpaper. They live in `config/kitty/kitty.conf`, not in zsh — see below.

## The terminal

kitty is the only terminal on either machine, so `config/kitty/kitty.conf` is where the colours live.

- **The scheme is "Skylight", derived from `config/wallpapers/LSZEE Skylight Red Rocks.jpg`** — the same palette as the Trilium theme built from that image, so notes and terminal match. The image is indigo haze (over a million pixels at hue 240) with a warm tail through magenta into coral and a thin cool one into mint. Two values in `kitty.conf` are *not* from the palette and are commented as such: the wallpaper has essentially no green (161 desaturated pixels at hue 165), which Trilium never needed and a terminal does, so `color2`/`color10` are the mint rotated to hue 140 at the palette's own saturation and value; and the palette names only `mint-dim` and `coral-dim`, so the dim amber, steel and magenta are the transform those two encode (saturation +0.077, value −0.175) applied to their bright counterparts.
- **The colours are terminal config, not shell config, and that is load-bearing.** `~/.zshrc` is this same repo on both machines, so a shell that painted its own background would paint it again on the far side of an ssh — the remote would come up Skylight-blue and `ssh-tint.zsh` below would have nothing to do. `kitty.conf` is read only by the terminal in front of you. It also means the window is the right colour on its first frame, with no flash of stock black while zsh starts, and the dropdown terminal, being an ordinary kitty, inherits it for free.
- **`config/zsh/env/ssh-tint.zsh` wraps `ssh` and tints the background oxblood (`#2A1518`) for the life of the session**, so a remote shell never looks like a local one. The shell has to do this because kitty does not know what is running inside it. Details worth not re-deriving:
  - It emits **OSC 11** to set the background and **OSC 111** to reset it. Resetting is what keeps the script from drifting out of sync with the theme — it never needs to know that local is `#161A31`. No `allow_remote_control` and no listen socket, unlike `kitty @ set-colors`.
  - The restore is a zsh **`always` block**, so Ctrl-C and a dropped connection restore the colour too; the terminal cannot get stranded oxblood. The remote's exit status is passed through.
  - It **no-ops when `$SSH_CONNECTION` is already set.** Restoring on a nested hop's exit would hand the outer session back its Skylight blue while still remote — the one state the whole thing exists to make impossible.
  - It **no-ops when stdout is not a tty**, so `ssh host cat file > out` is left alone, and `git push` is unaffected either way (it spawns `ssh` directly, and shell functions are not inherited by non-interactive subprocesses).


## The niri / Wayland session (spellbook only, so far)

The spellbook can boot either i3 on X or **niri** on Wayland; the desktop is still i3-only. What changes on the Wayland side:

- **Login manager.** `greetd` replaces LightDM, running **noctalia-greeter** (`machines/spellbook/greetd/config.toml` → `/etc/greetd/config.toml`, linked by the spellbook's `init.zsh`). The command is `noctalia-greeter-session`, never the bare `noctalia-greeter`: the greeter is a Wayland client, and the wrapper is what starts the bundled wlroots compositor it draws into. The session picker lists everything in `/usr/share/wayland-sessions` and `/usr/share/xsessions`, so i3 stays selectable. greetd and LightDM both claim `display-manager.service`, so only one can be enabled — which is why the greetd half is spellbook-only and why LightDM is disabled, not removed (`sudo systemctl disable --now greetd && sudo systemctl enable --now lightdm` from a text console is the way back).
- **The avatar above the username is not a greeter setting.** `greeter.toml` has no key for it; noctalia-greeter asks AccountsService for the user's `IconFile` and draws whatever that points at, so the picture is set with `init/avatar.zsh` from the committed `config/avatar.png`, not with greeter config. Two things make the obvious approaches fail. AccountsService's default answer is `$HOME/.face`, which the greeter — running as the unprivileged `greeter` user — can never read through a 0700 `$HOME`, the same trap as the `i3 (xprofile)` `.desktop` entry below; and the image must therefore be a real copy outside `$HOME`, never a symlink back into the repo. `SetIconFile` handles both: the daemon reads the source as root and copies it to `/var/lib/AccountsService/icons/<user>`, world-readable. It also caps the icon at 1 MiB, and the greeter rejects progressive JPEGs, so the source is a square ~512px PNG. lightdm-gtk-greeter reads the same property, which is why this step is shared rather than spellbook-only.
- **Shell.** **Noctalia Shell** (`noctalia --daemon`, started by `spawn-at-startup`) is bar, launcher, notifications, control centre, lock screen, OSDs and wallpaper in one process. It replaces i3bar/i3status, dunst, nm-applet, Ulauncher and `bin/wallpaper`; none of those are started under niri. Keybinds drive it through `noctalia msg …`.
- **A logged-out Noctalia can outlive its session and then block its own replacement.** The symptom is a login with no bar, no launcher and nothing obviously wrong in any log. The chain: `noctalia` ignores `SIGTERM`, so on logout systemd waits out its stop timeout before `SIGKILL`ing it (`app-niri-noctalia-N.scope: Stopping timed out. Killing.`); `spawn-at-startup` puts it in **`app.slice`**, not the `session.slice` that `niri.service` lives in, so it is not torn down with the compositor; and its single-instance lock, `/run/user/$UID/noctalia-wayland-1.lock`, is keyed on the Wayland socket **name**, which every niri instance reuses as `wayland-1`. Log back in inside that stop-timeout window and the corpse still holds the lock, so the new session's `spawn-at-startup` sees "already running" and exits silently — leaving a Noctalia attached to a compositor that no longer exists. `Linger` is `no`; this is a slow-shutdown-plus-fast-relogin race, not a lingering misconfiguration, so it shows up exactly when you are iterating on login.
  - **Diagnosing it takes one comparison.** `fuser -v /run/user/$UID/noctalia-wayland-1.lock` names the holder, and that PID's `NIRI_SOCKET` / `XDG_SESSION_ID` in `/proc/<pid>/environ` will point at a *different* niri than the live one (`niri msg version` reaches the live socket; `niri.service` prints its own in the journal as `IPC listening on:`). `/proc/<pid>/cgroup` showing `app.slice` rather than `session.slice` is the other half of the tell.
  - **Recovery is two commands.** `systemctl --user stop app-niri-noctalia-<N>.scope` (find it with `systemctl --user list-units 'app-niri-noctalia-*'`), then `niri msg action spawn -- noctalia --daemon`. Use the `niri msg action spawn` form, not a bare `noctalia --daemon` from a shell: it inherits the compositor's environment, so the new instance binds the live `NIRI_SOCKET` instead of whatever stale values the shell is carrying.
  - **The real fix is not done.** Making Noctalia a systemd user unit with `PartOf=niri.service` would tie its lifetime to the compositor and remove the race, but no packaged unit exists and it changes how the shell starts on every boot, so it is a deliberate change rather than a cleanup.
- **Role config works differently from i3's.** i3 pulls its role file in with `include $HOME/src/env/machines/${MACHINE_ROLE:-desktop}/i3/*.conf`, which works because i3 expands include paths with `wordexp(3)` and silently skips an empty glob. **niri's `include` expands `~` and nothing else** — no environment variables, no globs — and a file it cannot read is a parse error that rejects the entire config. So the role cannot be named from inside the config, and the indirection lives in `init/links.zsh` instead: it links `machines/<role>/niri/role.kdl` to the fixed path `~/.config/niri/role.kdl`, which `config/niri/config.kdl` includes on its last line. Both roles therefore ship a `niri/role.kdl` (the desktop's is comment-only) for the same reason every role ships at least one `i3/*.conf`.
- **Two file links, not one directory link.** `~/.config/i3` is a single directory symlink; niri gets `config.kdl` and `role.kdl` linked individually, because they come from different places in the repo.
- **Validation.** `niri validate -c <file>` is the closest thing this repo has to a test for it, and it is worth running on both roles after a change (point `HOME` at a throwaway directory holding a `.config/niri/role.kdl` link to check the other role's). niri also watches the live config and reloads on save, keeping the last good version when a new one fails to parse.
- **What does not survive the move.** `~/.xprofile` is a display-manager convention, so nothing in it runs under niri — that is fine, since the role split no longer needs `MACHINE_ROLE` and niri handles hotplug itself (no autorandr). X-only tools lose their bindings: `flameshot` (its legacy X11 grab sees only XWayland), `autorandr`, and `machines/spellbook/bin/monitor-output`'s X resources. Noctalia covers screenshots and display settings. X *applications* still work — niri spawns `xwayland-satellite` on demand and exports `DISPLAY` itself, so there is nothing to configure beyond installing the package.
- **Picking i3 from the greeter needs the `i3 (xprofile)` entry, not the stock `i3`.** greetd starts X sessions with `startx <wm>`, and an explicit client means `startx` reads neither `~/.xinitrc` nor `~/.xprofile` — so the stock entry gives an i3 with no `MACHINE_ROLE` (the spellbook silently loads the *desktop* role), no `autorandr --change`, and no `monitor-output`. `bin/i3-xsession` sources `~/.xprofile` and then execs i3; `machines/spellbook/xsessions/i3-xprofile.desktop` is the picker entry that runs it. Three details, each found the hard way and each worth not re-deriving:
  - **The `.desktop` is copied into `/usr/local/share/xsessions`, not symlinked into the repo.** The greeter parses it as the unprivileged `greeter` user, and `$HOME` is `drwx------` — a symlink into `~/src/env` is unreadable to that user and the entry just never appears. Only the `Exec` target can be a repo symlink, because that runs after authentication as the logging-in user.
  - **The entry is named `i3 (xprofile)`, not `i3`.** The greeter de-duplicates the picker by `Name=`, and nothing reveals which of two same-named entries wins — so shadowing the stock entry would be a coin flip between the fixed session and the broken one.
  - **No `TryExec=`.** The greeter ignores it; a greeter that honours it would evaluate it as its own unprivileged user, fail to stat the symlink target inside `$HOME`, and hide the entry for the wrong reason.

  `noctalia-greeter sessions` prints the picker list exactly as the greeter builds it, and is the way to check any of this (the spellbook's `init.zsh` warns if the entry is missing). It also honours `NoDisplay=true` but ignores a missing `Exec`.
- **The dropdown terminal is `bin/dropterm-niri`, a floating window on a scratchpad workspace — not `kitten quick-access-terminal`, and not tdrop.** Same key as i3 (`Mod+grave`), placed by the `^dropterm$` window rule in `config/niri/config.kdl`. It was the quick-access kitten, and the kitten is why it is not: that window is a **wlr-layer-shell surface, which takes its output at creation and can never be moved**, so the dropdown was stuck on whichever monitor first opened it (in practice the laptop panel, while focus was on a desk monitor). kitty does spawn it with `--move-to-active-monitor`, but `kitten panel --help` documents that flag as *macOS only* — on Wayland it is a silent no-op, so nothing in kitty or niri could relocate it. An ordinary toplevel niri moves between outputs freely, and moving a window does not touch the process behind it, so the dropdown is now a normal floating kitty and the script is the i3 scratchpad pattern: hiding parks it on the `scratch` workspace, showing pulls it to the focused monitor. **It follows focus and never restarts the shell inside it** — verified across all three outputs with the pid unchanged. Four things worth not re-deriving:
  - **`scratch` must be a declared workspace, and it is declared per role** (`machines/<role>/niri/role.kdl`). niri has no minimize, so hiding is a move to a workspace nothing is ever focused to; an *undeclared* workspace is cleaned up the moment the window leaves it, and the next hide would have no name to move to. Declaring it makes it persistent — at the cost of a slot in Noctalia's workspace list, which is why the spellbook pins it to `eDP-1` rather than the desk monitor.
  - **The window rule's `default-` properties are open-time only, so the script reasserts width and position after every move.** A floating window carries its old size across a cross-monitor move instead of being re-fitted, and these outputs disagree on logical width (both externals 3072, the built-in panel 2560) — without the reassert the dropdown keeps the width it was born with and hangs 512px off the side of the narrow one. `set-window-width 100%` lets niri do the per-output arithmetic.
  - **The binding is `spawn-sh` with an absolute `$HOME` path, not `spawn "dropterm-niri"`.** niri inherits PATH from greetd, which has no `~/src/env/bin`, so a bare name finds nothing and fails *silently*. The old binding got away with `spawn "kitten"` only because that is in `/usr/bin`. Same reason the `spawn-sh-at-startup` lines spell the path out.
  - **The `flock` came back.** The kitten serialised on kitty's single-instance socket, so two fast presses could not race; an ordinary `kitty` has no such socket, which brings back exactly the double-dropdown race tdrop had under i3.

  What is given up by not being a layer surface: `layer overlay` drew above fullscreen windows. A floating toplevel sits above tiled windows but not above a fullscreen one.
- **Noctalia needs a Secret Service provider, and `libsecret` is not one.** Its calendar (the Google OAuth refresh token), its own encrypted-storage key and its clipboard history all persist through `org.freedesktop.secrets`, and with no daemon owning that name they refuse with "No Secret Service available. Start / install Gnome-keyring, kwallet or keepassXC". `libsecret` is the *client* half and was already installed as a transitive dependency, which is exactly the state that produces the error. `gnome-keyring` (spellbook `packages.txt`) is the provider: no KDE stack, and the only one of the three with a PAM module. Several things worth not re-deriving:
  - **Nothing in this repo starts it.** The package ships both `gnome-keyring-daemon.socket` (enabled, `WantedBy=sockets.target`, listening on `%t/keyring/control`) and `/usr/share/dbus-1/services/org.freedesktop.secrets.service`, so the daemon comes up inside `user@.service` on its own — in practice from the socket unit, with D-Bus activation as the fallback. There is deliberately no `spawn-at-startup` line for it, unlike `noctalia --daemon`.
  - **Auto-unlock is pure PAM, and it only ever unlocks the keyring named `login`.** `machines/spellbook/init.zsh` adds three `pam_gnome_keyring.so` lines via `sudo_pam_add_line` — `auth` in `/etc/pam.d/greetd` (which must land *after* `auth include system-local-login`, the include that actually collects the password), `session … auto_start` appended after `pam_systemd.so`, and `password` in `/etc/pam.d/passwd` so the keyring is re-keyed when the login password changes. A keyring created interactively before any of that exists is called `Default_Keyring`, carries its own password, and also holds the `default` alias, so all three lines can be correct and still do nothing. Deleting it and letting PAM recreate `login.keyring` is the only fix.
  - **`~/.local/share/keyrings/default` is not the thing to check, and its absence is normal.** That file only exists when something set the alias explicitly; with just a login keyring it is usually missing, and gnome-keyring resolves `default` → `login` anyway. Init's warning therefore fires only when the file *exists and names something other than* `login` — warning on absence would fire on every correctly-configured machine. The authoritative checks are `busctl --user call org.freedesktop.secrets /org/freedesktop/secrets org.freedesktop.Secret.Service ReadAlias s default` (expect `/org/freedesktop/secrets/collection/login`) and a `secret-tool store` / `secret-tool lookup` round trip that returns the value without a popup. `busctl --user get-property … /collection/login … Locked` should be `false`.
  - **Deleting a keyring file does not reach the running daemon, and the stale daemon is what you will actually be debugging.** `gnome-keyring-daemon` holds its collections in memory: delete `Default_Keyring.keyring` under a live daemon and it keeps serving a phantom `/collection/Default_5fKeyring`, never exposes the new `login.keyring`, accumulates stuck `/prompt/pN` objects, and logs `gkm_object_expose_full: assertion 'GKM_IS_OBJECT (self)' failed`. The giveaway is the `Collections` property and the introspected object tree disagreeing — the property lists `login` while `busctl --user tree` has no such path and `get-property` on it says "Object does not exist". `systemctl --user restart gnome-keyring-daemon.service` (or a re-login) clears it. Always restart after touching the keyring files.
  - **Transient duplicate daemons during that churn are a symptom, not the bug.** Three things can start the service — the enabled `gnome-keyring-daemon.socket`, the D-Bus activation file, and PAM's `auto_start` — and mid-thrash you can catch two running, logging `discover_other_daemon: 1` and "The Secret Service was already initialized". The steady state is one daemon, the socket unit's (`--components=pkcs11,secrets --control-directory=%t/keyring`), owning `org.freedesktop.secrets`; `--start` is documented as "start a daemon *or initialize an already running daemon*", so the overlap is by design. Do not go removing `auto_start` over it.
  - **All three are `optional`, not `required`.** PAM ignores an optional module that fails *or* cannot be loaded, so a renamed or removed gnome-keyring degrades to "the keyring does not unlock" instead of "the greeter does not accept your password".
- **Noctalia plugins are enabled, not installed.** Noctalia ships the official and community plugin repos as *config defaults* (`[[plugins.source]]`), keeps their git mirrors under `~/.local/state/noctalia/plugins/sources/`, and materializes a plugin out of the mirror into `plugins/materialized/` the first time it is enabled — so the whole install is putting the plugin's id in `[plugins] enabled`, and the default `auto_update = "all"` keeps it current. `noctalia msg plugins list` prints every plugin in both sources with its state; nothing is downloaded per-plugin. The spellbook enables two, both battery-related: `piero-93/battery-power-management` ("Battery & Power Management" — a bar widget with charge, live watts and the active power profile, plus a panel that switches it) and `yocraft/battery-widget` ("Battery Widget" — the same numbers as a desktop/lockscreen widget). Three things about doing that from init:
  - **`noctalia msg plugins enable` is IPC to a running shell, so init cannot use it.** On a new spellbook init finishes before anything has ever logged into niri. `machines/spellbook/init.zsh` therefore edits `[plugins] enabled` in `settings.toml` directly, with `machines/spellbook/noctalia-settings-ensure.awk` — the repo's one awk program rather than zsh, because it is a line-oriented rewrite that has to preserve the rest of the file byte for byte. A `settings.toml` holding nothing but those keys is valid (`noctalia config validate` agrees), because Noctalia merges it over its defaults and fills the rest in on its first save, so seeding one on a machine that has never started the shell is safe.
  - **`settings.toml` is state, not config, and is never tracked here** — the same call `greeter.toml` gets, for stronger reasons: it holds absolute `$HOME` paths (so two machines with different usernames could never share one), the hand-tuned bar order, the calendar accounts, and a lockscreen widget layout keyed on the dock's monitor names, and Noctalia rewrites the whole file whenever anything changes in its settings UI. Init sets the two keys it needs and leaves the rest alone. It also does **not** place the widgets — which widget sits where is bar/desktop-widget layout in that same file, so placing them would overwrite a hand-tuned list on every run. The bar's widget picker and `noctalia msg desktop-widgets-edit` are the way in. One detail that makes the "did anything change?" check work: awk always terminates its last line and Noctalia writes the file *without* a trailing newline, so init compares against a newline-normalized copy or it would rewrite and reload on every single run.
  - **The plugin's `battery_device` defaults to `BAT0` and it does not autodetect**, so on this Framework 16 — whose battery is `BAT1` — a plugin left at its default reads a sysfs path that is not there and shows nothing. Init takes the first `/sys/class/power_supply/BAT*` it finds, and writes it only when the key is absent so a hand-edited choice survives. The charge-limit slider, by contrast, cannot work here at all: this machine exposes no `charge_control_end_threshold`, which is also why init never runs the plugin's bundled `setup-threshold-permissions.sh` (it would create a `battery_ctl` group and a udev rule granting write access to a file that does not exist).
- **`/etc/pam.d` files are edited in place, never linked.** They belong to the package that ships them (greetd, pambase): a symlink into this repo would be clobbered on upgrade, and a missing one is a login failure. `sudo_pam_add_line` therefore copies its one-time backup to `FILE.bak` rather than using `backup_once`'s `mv`, and the backup is inert because PAM resolves a service by exact filename. It is idempotent on the (type, module) pair rather than the literal line, so a hand-edited control flag is left alone instead of being shadowed.

## Provisioning flow

`init/init.sh [--desktop|--spellbook] [--links-only] [--force-role]` installs zsh and execs `init/init.zsh` with `MACHINE_ROLE` set. `init.zsh` sources each step **in its own subshell** by absolute path off `ENV_DIR`, so a failing step (or a stray `exit`) is reported and init continues; it prints a summary of failed steps at the end. Every step is safe to re-run. Order:

1. `fs.zsh` — `~/src`, `~/.config`, `~/.ssh` (0700), `~/docs/obsidian_vaults` (never the vault itself)
2. `role.zsh` — link `~/.config/machine-role.env`
3. `pacman.zsh` — link `pacman.conf`, install git, bootstrap yay (`yay.zsh`), `yay -Syu`, install `config/packages.txt` + `machines/<role>/packages.txt`. Interactive on purpose (no `--noconfirm`): the desktop gaming packages raise provider prompts (`lib32-vulkan-driver`) where the default pick is AMD, not NVIDIA
4. `gh-login.zsh` — `gh auth status`; only when logged out, `gh auth login --git-protocol ssh --web` (device code, works from a text console; offers to generate and upload an ssh key), then init continues on its own
5. `antidote.zsh`, `node.zsh` — antidote clone; latest node via the `nvm` package
6. `links.zsh` — zsh files, `~/env`, `~/.config/i3` (whole directory), the two niri files, kitty, `~/.ssh/config` (file only), `~/.xprofile` (never `~/bin`); returns non-zero if any link failed
7. `claude.zsh` — link `CLAUDE.md`, `settings.json` and every `claude/user-skills/*` dir; copy `config.sample.json` → `~/.claude/config.json` only if missing (never overwritten; prints a reminder to paste the Obsidian key). The local plugin marketplaces stay as the committed `~/src/<name>` directory sources in `settings.json`: Claude Code expands `~` itself when it registers them in `~/.claude/plugins/known_marketplaces.json`, so init never rewrites the tracked file (it used to, with a username-specific absolute path)
8. `avatar.zsh` — set the login-screen avatar from the committed `config/avatar.png` via AccountsService's `SetIconFile`, which copies it to `/var/lib/AccountsService/icons/<user>` and persists `Icon=` itself; a no-op when the installed copy already matches
9. `marketplaces.zsh` — `gh repo clone` the local plugin marketplaces into `~/src` (skip if present)
10. `git.zsh` — add `git/gitconfig` to the global `include.path` once
11. `shell.zsh` — `chsh` to zsh if needed
12. `spotify-mcp.zsh` — clone `spotify-mcp-server`; `npm install && npm run build` whenever `build/index.js` is missing (so a failed first build is retried on the next run); copy `spotify-config.sample.json` into it once (real file, never a link); register the server with Claude Code at user scope via `bin/claude-hook-node`, guarded on `claude mcp get spotify` because re-adding an existing name errors; `npm run auth` only once the build exists, the client id/secret are filled in and no `refreshToken` is stored
13. `machines/<role>/init.zsh` — role hook (desktop: LightDM drop-in via `sudo`; spellbook: autorandr drop-in, `video` group, the greetd / Noctalia Greeter setup that hands `display-manager.service` over from LightDM, the `i3 (xprofile)` session entry, the `pam_gnome_keyring.so` lines that auto-unlock the keyring, the logind lid drop-in, and the two Noctalia battery plugins)

`--links-only` runs only steps 1, 2, 6, 7, 8, 10 and 13: no packages, network, or `chsh`. Steps 3, 4, 9, 12 need sudo/network and are the ones to stub when testing.

### The role guard (`init/init.sh`)

**A role flag is effectively mandatory on a provisioned machine.** `init.sh` refuses to run when the role it was asked for contradicts the `MACHINE_ROLE` already published in `~/.config/machine-role.env`, naming the flag that was missing; `--force-role` is the escape hatch for genuinely re-provisioning a box under the other role. A machine with no role file yet — a real first run — is never blocked, and neither is a role file with no parseable value.

This exists because the argument default is the one place `${MACHINE_ROLE:-desktop}` is a trap rather than a safety net. A flagless `init.sh` on the spellbook is *silent* and the damage is split across two steps: `role.zsh` repoints `~/.config/machine-role.env`, so every new shell and the i3 include switch roles, and `links.zsh` repoints `~/.config/niri/role.kdl` at `machines/desktop/niri/role.kdl` — which is comment-only, so niri's config watcher reloads a config that **parses perfectly** and has none of the spellbook's binds, named workspaces or window rules. `niri validate` still says "config is valid". The role-only directories `links.zsh` guards with `[[ -d ... ]]` (`autorandr`, `wireplumber`, `ulauncher`) survive untouched because the desktop ships none of them, so the breakage looks partial, which makes it harder to place rather than easier. Packages are not touched either way, and `link_path` replaces symlinks without backing them up, so there is nothing to restore — the repair is re-running with the right flag.

Two limits worth knowing. The guard reads the role file, which is the very thing a wrong run rewrites, so it protects against the *first* mistake and not a repeat while the file is still wrong — and for the same reason the repair itself needs `--force-role` (or a hand-fixed symlink) to get past it. Nothing cross-checks the role against the hardware.

### Linking rules (`init/lib.zsh`)

`link_path SRC DEST` (and `sudo_link_path` for `/etc`) is used for every link init makes: no-op if `DEST` already points at `SRC`; a symlink pointing elsewhere is replaced; a real file/dir is moved to `DEST.bak` once (a later run never overwrites an existing backup — it gets a timestamp suffix instead). Symlinks are always replaced, never linked into, so re-running can't create nested links inside a target directory. Every mutation (`mv`, `rm`, `mkdir`, `ln`) is checked: on failure the helper prints `FAILED to link ...` on stderr and returns non-zero, so the step fails and shows up in init's summary instead of printing a `linked` line that never happened.

## Git helper scripts

`git/*.sh` are exposed as git subcommands via aliases in `git/gitconfig`, which `init/git.zsh` pulls into the global config with `git config --global include.path`. This gives `git update` / `git cleanup` / `git rename-branch`:
- `git-update.sh` — stash, checkout default branch (`master` by default, or `$1`), pull, return to original branch, rebase onto default, re-apply stash.
- `git-cleanup.sh` — prune remote-tracking refs and delete local branches whose upstream is `: gone]`.
- `git-rename-branch.sh` — rename a branch locally and recreate it on the remote (`git rename-branch old new`).

`git-update.sh` defaults the trunk to `master`; this repo's own trunk is `main`, so pass it explicitly when running here.

## Conventions

- New shell scripts are zsh (`#!/usr/bin/zsh`). Exceptions: `init/init.sh` (bash bootstrap), `config/.xprofile` and the `machines/*/xprofile.sh` fragments it sources (POSIX sh). Older files with other shebangs are normalized only when touched.
- `sudo` cannot run from Claude's shell (no TTY); don't run init, package installs, `chsh`, or anything touching `/etc`. Verify with `zsh -n`, `sh -n`/`bash -n`, and by running the link steps against a throwaway `HOME` with `sudo`/`gh` stubbed.
- `alias.zsh` assumes `lsd`, `vim`, and `xclip` are installed.
- `claude/settings.json` is written back to by Claude Code (through the `~/.claude/settings.json` symlink), so expect it to show up modified.
